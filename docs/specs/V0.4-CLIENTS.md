## 1. Objectifs

Doter chaque salon d'un **fichier clients fiable, rapide à utiliser sur iPhone et conforme au RGPD**, relié au planning :

| # | Besoin | Résultat attendu |
| --- | --- | --- |
| 1 | Fiches clients et coordonnées | Créer / consulter / modifier une fiche en moins de 15 s au comptoir |
| 2 | Historique des rendez-vous | Passés, à venir, annulés, absences (no-show), montants |
| 3 | Préférences et prestations habituelles | Collaborateur préféré, prestations favorites, créneaux préférés, notes techniques |
| 4 | Recherche rapide et filtres | Résultat en < 300 ms sur 20 000 fiches, tolérant aux fautes et aux accents |
| 5 | Gestion des doublons | Détection à la saisie + fusion assistée, sans perte d'historique |
| 6 | Consentements marketing | Par canal et par finalité, historisés, prouvables |
| 7 | Export, rectification, suppression | Droits RGPD exerçables en 2 gestes depuis la fiche |
| 8 | Informations sensibles (soins esthétiques) | Protection renforcée, consentement explicite, accès tracé |
| 9 | Isolation stricte | Aucune fuite entre entreprises **ni entre établissements** non autorisés |

**Hors périmètre V0.4** (proposé pour la suite) : envoi de campagnes marketing, rappels SMS automatiques, fidélité, réservation en ligne par le client, **photos avant/après** (donnée personnelle, parfois sensible : nécessite Supabase Storage + politique dédiée → V0.5).

## 2. Principes directeurs

1. **Isolation by design** : `company_id` sur chaque table, RLS systématique, accès par établissement comme en V0.3.
2. **Minimisation** : **un prénom OU un nom suffit** (D4) ; téléphone et e-mail facultatifs ; les **clients de passage** restent possibles sans fiche (libellé libre sur le rendez-vous). Date de naissance : **jour et mois uniquement**, facultatifs, sans année (D5).
3. **Séparation des données sensibles** : les informations de santé liées aux soins (allergies, contre-indications, grossesse, traitements) sont **isolées dans une table dédiée**, jamais lisibles directement, toujours via une fonction serveur qui **vérifie le consentement explicite et journalise chaque accès**.
4. **Écritures sensibles côté serveur** : fusion, anonymisation, export, consentements → RPC `private` + enveloppes `SECURITY INVOKER` (modèle V0.2/V0.3).
5. **Traçabilité** : `audit_log` étendu (création, modification, fusion, export, anonymisation, accès aux données sensibles).
6. **Données fictives uniquement** dans les tests et la démo (domaine `.example`, numéros de la plage fictive `+33 6 39 98 xx xx` réservée par l'ARCEP à la fiction).

## 3. Modèle de données (proposition)

### 3.1 `clients`
| Colonne | Type | Règles |
| --- | --- | --- |
| `id` | uuid PK | |
| `company_id` | uuid FK | tenant, immuable |
| `home_establishment_id` | uuid | établissement de rattachement (FK composite) |
| `first_name` | text | 0–60 |
| `last_name` | text | 0–80 — **contrainte : prénom OU nom renseigné (D4)** |
| `email` | text | normalisé, unique par entreprise — **colonne non lisible via l'API** (D2) |
| `phone_e164` | text | E.164, unique par entreprise — **colonne non lisible via l'API** (D2) |
| `email_masked`, `phone_masked` | colonnes calculées | `l•••@exemple.fr`, `+33 •• •• 12 34` — seules versions lisibles directement |
| `birthday` | `smallint` mois + `smallint` jour | optionnels, sans année |
| `preferred_locale` | `app_locale` | fr / en / es / de |
| `preferred_staff_id` | uuid | collaborateur préféré |
| `general_note` | text ≤ 500 | **non sensible** (ex. « préfère le thé ») — avertissement à la saisie |
| `tags` | text[] ≤ 10 | ex. « VIP », « Étudiant » |
| `status` | enum | `active` / `archived` / `anonymized` |
| `merged_into` | uuid | renseigné quand la fiche a été fusionnée |
| `search_vector` | colonne générée | `unaccent` + minuscules (nom, prénom, e-mail, téléphone) |
| `created_by`, `created_at`, `updated_at`, `last_visit_at` | | `last_visit_at` mis à jour par trigger |

Index : GIN trigramme (`pg_trgm`) sur `search_vector`, B-tree sur `(company_id, last_name, first_name)`, unicité partielle sur e-mail et téléphone.

### 3.2 Préférences et fiche technique (non sensibles)
- `client_favorite_services (client_id, service_id, company_id)` — prestations habituelles (aussi déduites de l'historique).
- `client_technical_notes (id, client_id, company_id, kind, content ≤ 1000, created_by, created_at)` — ex. **formules de coloration**, type de cheveux, longueur, matériel. `kind` ∈ `color_formula`, `hair`, `skin_type`, `nails`, `other`.
- Créneaux préférés : `preferred_days smallint[]`, `preferred_time_of_day` (`morning`/`afternoon`/`evening`).

### 3.3 Informations sensibles — `client_health_notes` (protection renforcée)
| Colonne | Détail |
| --- | --- |
| `client_id`, `company_id` | 1–1 avec la fiche |
| `allergies`, `contraindications`, `treatments`, `pregnancy` (booléen), `other` | texte ≤ 1000 |
| `consent_id` | **FK obligatoire** vers le consentement explicite « données de santé » (art. 9.2.a RGPD) |
| `updated_by`, `updated_at` | |

Mesures :
- **Aucun privilège `SELECT` direct** pour `authenticated` : lecture via `get_client_health_notes(client_id)` uniquement.
- La fonction vérifie : permission `client.health.read` + accès à l'établissement + **consentement actif** ; sinon refus.
- **Chaque lecture et écriture est journalisée** (`health_access_log` : qui, quand, quelle fiche — sans contenu).
- **Chiffrement applicatif des champs** (pgcrypto, clé conservée dans Supabase Vault) en plus du chiffrement disque de Supabase. *(Décision D3.)*
- Retrait du consentement ⇒ **effacement immédiat** des données de santé (trigger).
- Affichage : section verrouillée 🔒, contenu masqué tant que l'utilisateur n'a pas touché « Afficher » (protection contre la lecture par-dessus l'épaule).

### 3.4 Consentements — `client_consents` (historique en ajout seul)
| Colonne | Détail |
| --- | --- |
| `client_id`, `company_id` | |
| `purpose` | `marketing`, `newsletter`, `appointment_reminders`, `health_data` |
| `channel` | `email`, `sms`, `whatsapp`, `postal`, `none` (pour `health_data`) |
| `status` | `granted` / `withdrawn` |
| `method` | `in_salon_verbal`, `in_salon_signed`, `online_form`, `import` |
| `wording_version` | version du texte présenté au client (preuve) |
| `captured_by`, `captured_at` | |

- **Jamais de mise à jour ni de suppression** (privilèges) : une nouvelle ligne à chaque changement ; vue `client_consent_status` = dernier état par (finalité, canal).
- Rappels de rendez-vous : intérêt légitime / exécution du contrat (pas de consentement marketing requis), mais opposition possible.

### 3.5 Lien avec le planning
- `appointments.client_id uuid null` (FK composite `(client_id, company_id)`), ajouté par migration ; `client_label` conservé pour les clients de passage et pour l'historique anonymisé.
- Historique = requête sur `appointments` filtrée par `client_id` (RLS de la V0.3 inchangée : un collaborateur ne voit que l'historique **des établissements auxquels il a accès**).

## 5. Fonctionnalités détaillées

### 5.1 Recherche et filtres
- Barre de recherche **toujours visible** en haut de la liste ; recherche dès 2 caractères, tolérante aux accents (`unaccent`) et aux fautes (`pg_trgm`, similarité ≥ 0,3), sur nom, prénom, e-mail, téléphone (chiffres seuls).
- RPC `search_clients(q, filters, cursor)` : **50 résultats maximum par page**, pagination par curseur ; **pas de liste complète sans critère pour le rôle `staff`** (anti-aspiration du fichier).
- Filtres (chips) : établissement, tag, dernière visite (< 1 mois, 1–6 mois, > 6 mois), jamais venu, absences ≥ 2, consentement marketing (oui/non), anniversaire ce mois-ci.
- Tri : pertinence, nom, dernière visite.

### 5.2 Doublons
- **À la saisie** : dès que prénom + nom, e-mail ou téléphone sont tapés, appel à `find_duplicate_candidates()` ; bandeau « Fiche similaire : Léa B. (06 •• •• 12 34) — Ouvrir / Créer quand même ».
- **Règles de détection** (score) : e-mail identique (100), téléphone identique (100), nom + prénom très similaires (trigramme > 0,6) (60), même anniversaire (+20).
- **Fusion** `merge_clients(keep_id, merge_id, field_choices)` — **atomique** (une transaction, verrous `FOR UPDATE` sur les deux fiches) :
  1. champs retenus selon le choix de l'utilisateur ;
  2. rendez-vous, notes techniques, prestations favorites rattachés à la fiche conservée ;
  3. **consentements : historique des deux fiches conservé** ; l'état courant retenu est **le plus restrictif** (un retrait l'emporte) ;
  4. données de santé : conservées seulement si un consentement santé actif existe sur la fiche finale ;
  5. fiche fusionnée → `merged_into`, puis anonymisée ; audit.
- Écran de fusion iPhone : comparaison champ par champ (deux colonnes, choix par bouton radio).

### 5.3 Fiche client
- En-tête : initiales colorées, nom, tags, **actions rapides** : 📞 appeler (`tel:`), 💬 SMS (`sms:`), ✉️ e-mail (`mailto:`), 📅 **Prendre rendez-vous** (ouvre le planning prérempli).
- Onglets (défilement horizontal) : **Aperçu** · **Historique** · **Préférences** · **Fiche technique** · **Santé 🔒** · **Consentements** · **Données (RGPD)**.
- Historique : liste chronologique (à venir / passés), statut, collaborateur, prestation, montant ; compteurs (visites, CA total, absences).

### 5.4 RGPD : export, rectification, suppression
| Droit | Mise en œuvre |
| --- | --- |
| Accès / portabilité | `export_client_data(client_id)` → JSON lisible + CSV (fiche, historique, préférences, consentements ; **données de santé incluses seulement si `client.health.read`**). Journalisé. Partage via la feuille de partage iOS. |
| Rectification | Modification directe, tracée dans `audit_log` (champ modifié, sans valeur). |
| Effacement | `erase_client(client_id, reason)` : **anonymisation** — suppression des coordonnées, notes, préférences, données de santé ; consentements réduits à une preuve minimale ; les rendez-vous passés sont conservés sous « Client supprimé » pour les **obligations comptables (10 ans, art. L123-22 C. com.)**. Confirmation par saisie du mot « SUPPRIMER ». |
| Opposition marketing | Retrait d'un consentement en 1 geste depuis l'onglet Consentements. |
| Conservation | Clients sans visite depuis **3 ans** (recommandation CNIL) : signalés dans un tableau « À revoir » ; anonymisation **proposée** au gérant (tâche planifiée `pg_cron`, décision D6). |
| Information | Notice client imprimable / QR code (FR/EN/ES/DE) générée depuis les paramètres du salon. |

## 6. Interface iPhone (identité SOLUSSIMO conservée)

- **Liste** : recherche collante sous l'en-tête, chips de filtres défilantes, cartes 64 px (initiales, nom, dernière visite, pastille consentement), bouton flottant « + » au-dessus de la barre d'onglets, zones tactiles ≥ 44 px, respect des zones sûres.
- **Création** : feuille du bas (composant `Sheet` V0.3) — prénom, nom, téléphone (clavier numérique, pays par défaut de l'établissement), e-mail ; consentements proposés en fin de formulaire (cases **non cochées** par défaut).
- **Planning** : dans la feuille de rendez-vous, le champ « Client » devient un **sélecteur avec recherche** (+ « Nouveau client » en ligne) ; « Client de passage » reste possible.
- **Couleurs** : turquoise `#008B8B` (actions), turquoise clair `#BFEAE7` (sélections), or doux `#C4A875` (VIP, alertes douces), rouge réservé aux actions destructives.
- **Accessibilité** : libellés ARIA, contrastes AA, Dynamic Type respecté (tailles en `rem`).
- **Langues** : nouveaux espaces `clients.*`, `consents.*`, `gdpr.*`, `health.*` en FR/EN/ES/DE ; test de parité existant étendu ; formats de téléphone via `libphonenumber-js` (≈ 40 Ko, chargé à la demande) ; textes de consentement **versionnés par langue** (`wording_version`).

## 11. Critères d'acceptation (démonstration sur iPhone)

1. Créer un client en < 15 s, avec alerte si une fiche similaire existe.
2. Retrouver un client en tapant 3 lettres (avec ou sans accent).
3. Réserver depuis la fiche client ; voir le rendez-vous dans l'historique.
4. Enregistrer/retirer un consentement SMS ; l'historique conserve les deux événements.
5. Fusionner deux doublons ; aucun rendez-vous perdu.
6. Exporter les données d'un client et les partager via iOS ; supprimer (anonymiser) une fiche.
7. Un collaborateur sans habilitation ne voit pas l'onglet Santé ; un collaborateur d'une autre entreprise ne voit rien.
8. Toute l'interface disponible en FR, EN, ES, DE.

## 12. Étude de faisabilité technique (avant développement)

Vérifications effectuées le 22/11/2026 sur le projet Supabase **dev** (requêtes en lecture seule) et en local.

### 12.1 Chiffrement des données de santé (D3)
| Élément | Constat | Conséquence |
| --- | --- | --- |
| `supabase_vault` 0.3.2 | **installé** ; `vault.create_secret` utilisable par le propriétaire de la base ; `vault.decrypted_secrets` **non lisible** par `authenticated` / `anon` | La clé de chiffrement est stockée dans le **Vault** (chiffrée au repos, absente des sauvegardes en clair et du dépôt) |
| `pgcrypto` 1.3 | installé | Chiffrement **AES-256** (`pgp_sym_encrypt`, mode `cipher-algo=aes256`) |
| `pgsodium` | non installé (déprécié côté Supabase) | Non utilisé |

**Gestion des clés** : une clé aléatoire de 256 bits est **générée côté serveur** par la migration (`gen_random_bytes(32)`) et déposée dans le Vault sous le nom `solussimo_health_key_v1` — elle n'apparaît ni dans le dépôt ni dans l'historique des migrations. Chaque ligne chiffrée mémorise le nom de sa clé (`key_name`), ce qui permet une **rotation** (nouvelle clé `_v2`, re-chiffrement par une fonction dédiée, retrait de l'ancienne).

**Limites assumées** : le chiffrement protège contre la lecture des sauvegardes, des exports SQL, de l'éditeur de tables et toute exposition accidentelle par l'API ; il ne protège pas contre un administrateur Supabase disposant des droits du propriétaire de la base (qui peut lire le Vault). Ce risque résiduel est couvert par le contrat de sous-traitance (DPA) Supabase et la restriction des accès au tableau de bord.

**Côté local / CI** : un stub minimal du Vault (`vault.create_secret`, `vault.decrypted_secrets`) est ajouté au stub de test ; le code applicatif est identique.

### 12.2 Confidentialité des données de santé (D1)
- **Base légale** : consentement explicite (art. 9.2.a RGPD), recueilli et historisé (`client_consents`, finalité `health_data`), retirable à tout moment ; **le retrait efface immédiatement** les données de santé.
- **Analyse d'impact (AIPD)** : fortement recommandée (données sensibles) — l'activation exige que le propriétaire confirme l'avoir réalisée ou évaluée.
- **Hébergement HDS (France)** : la certification HDS vise l'hébergement de données de santé recueillies lors d'activités de prévention, de diagnostic ou de **soins médicaux** ; les instituts de beauté ne relèvent en principe pas de ce cadre, **mais ce point doit être confirmé par un conseil juridique** avant ouverture commerciale. Même logique pour § 22 BDSG (Allemagne) et LOPDGDD (Espagne).
- **Minimisation** : champs limités (allergies, contre-indications, traitements en cours, grossesse, autre), 1 000 caractères max, aucun diagnostic.
- **Accès** : jamais de lecture directe ; fonction serveur qui vérifie activation + habilitation + établissement + consentement, puis **journalise** (sans contenu).

### 12.3 Permissions (D2, D7)
| Contrainte | Solution retenue |
| --- | --- |
| PostgreSQL n'a qu'**un seul rôle** (`authenticated`) pour tous les utilisateurs de l'API : les privilèges par colonne ne distinguent pas owner / staff | Les colonnes `email`, `phone_e164` et la colonne de recherche sont **retirées des privilèges `SELECT`** pour tout le monde ; seules les versions masquées sont lisibles ; l'accès complet passe par une **fonction serveur** qui vérifie le rôle applicatif et journalise |
| Leçon V0.3 : `INSERT … RETURNING` évalue la politique de lecture sur la nouvelle ligne | Les politiques évaluent d'abord les colonnes de la ligne (entreprise, établissement de rattachement) |
| Marquage « Praticien de soins » : un responsable ne doit pas pouvoir s'auto-habiliter | Trigger : seul un owner/admin peut modifier ce marquage |
| Fusion concurrente (A←B et B←A simultanément) | Verrous `FOR UPDATE` pris **dans un ordre déterministe** (par identifiant) → aucune impasse, une seule fusion aboutit (test de concurrence) |
| Recherche massive (aspiration du fichier) | 50 résultats max ; le rôle `staff` doit saisir au moins 2 caractères |
