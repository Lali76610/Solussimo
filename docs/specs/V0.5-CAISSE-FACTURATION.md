# SOLUSSIMO V0.5 — Caisse, Encaissements et Facturation · Cahier des charges technique

> **Statut : proposition à valider — aucun développement engagé.**
> Base : V0.4 (Clients). Version du document : 1.0 — 22/11/2026.

> ⚠️ **Avertissement fiscal.** Ce document décrit des obligations **connues à la date de rédaction**, pays par pays, à titre de **cadrage technique**. Il ne constitue ni un avis juridique ni une garantie de conformité. Les règles fiscales et les calendriers de facturation électronique **évoluent souvent** : chaque pays activé devra être validé par un **expert-comptable ou un fiscaliste local** avant toute utilisation avec de vraies opérations. SOLUSSIMO ne revendique **aucune conformité universelle**.

## 2. Principes directeurs

1. **Montants en entiers** (centimes / unités mineures, `bigint`) — jamais de nombres à virgule flottante. Arrondis définis par pays et appliqués une seule fois, côté serveur.
2. **Écritures uniquement par RPC serveur**, comme pour les rendez-vous : le navigateur ne calcule jamais un total fiscal, il l'affiche.
3. **Inaltérabilité** : une vente validée n'est **jamais modifiée ni supprimée**. Toute correction passe par un **avoir** (écriture négative liée). Les brouillons non validés peuvent être abandonnés, et l'abandon est journalisé.
4. **Chaînage cryptographique** : chaque document validé (ticket, avoir, clôture) porte le hachage SHA-256 du précédent → toute altération en base est détectable.
5. **Numérotation continue sans trou**, par établissement, par série (tickets, factures, avoirs) et par année, attribuée dans la transaction de validation.
6. **Idempotence** : chaque validation de paiement porte une clé unique générée sur l'iPhone ; une requête répétée (réseau instable) ne crée **jamais** de double encaissement.
7. **Isolation** : `company_id` partout, RLS par établissement (modèle V0.3/V0.4), sessions de caisse liées à un établissement.
8. **RGPD** : minimisation (aucun numéro de carte, aucune donnée bancaire complète) ; les pièces comptables sont conservées au titre d'une **obligation légale** (art. 6.1.c RGPD), même si le client demande l'effacement de sa fiche (sa fiche est anonymisée, la pièce reste).
9. **Fiscalité par pays** : un **profil pays** décrit taux, mentions, séries, arrondis, exports et obligations techniques ; aucun pays n'est activé en production sans validation.

| **Suisse** | Pas de caisse certifiée imposée à notre connaissance. | Pas d'obligation générale d'e-facture ; QR-facture courante. | TVA 8,1 % ; conservation 10 ans |

## 4. Modèle de données (proposition)

Tous les montants sont en **unités mineures** (`bigint`) avec la `currency` (ISO 4217) de l'établissement.

### 4.1 Paramétrage
| Table | Contenu clé |
| --- | --- |
| `fiscal_profiles` | Par établissement : `country_code`, `currency`, `rounding_rule`, `invoice_mentions` (raison sociale, SIREN/USt-IdNr/NIF, TVA intracom., adresse du siège, capital, RCS…), `b2c_invoice_threshold`, mode fiscal (`demo`, `uncertified`, `certified`) |
| `tax_rates` | `company_id`, `country_code`, `code` (`standard`, `reduced`…), `rate_bp` (points de base : 2000 = 20 %), `valid_from`, `valid_to` — **datés**, jamais modifiés une fois utilisés |
| `payment_methods` | Par entreprise : `kind` (`cash`, `card`, `transfer`, `cheque`, `local`, `deposit`, `credit_note`), libellé, actif, ordre, `gives_change` (espèces) |
| `products` | Catalogue de vente minimal (nom, référence, prix TTC, `tax_rate_id`, actif) — **le stock arrive en V0.6** |
| `services` (existant) | Ajout de `tax_rate_id` |
| `discount_policies` | Par rôle : remise max (% et montant) sans validation ; motifs autorisés |

### 4.2 Caisse
| Table | Contenu clé |
| --- | --- |
| `cash_registers` | Établissement, nom, actif |
| `register_sessions` | `opened_at/by`, `opening_float`, `closed_at/by`, `counted_cash` (détail par coupure en JSON), `expected_cash`, `difference`, `difference_reason`, `z_report_id` ; **une seule session ouverte par caisse** (contrainte d'unicité partielle) |
| `cash_movements` | Entrées/sorties d'espèces hors vente (apport, retrait, dépôt banque) avec motif, auteur, validation |

### 4.3 Ventes, paiements, documents
| Table | Contenu clé |
| --- | --- |
| `sales` | Ticket : `establishment_id`, `register_session_id`, `client_id?`, `appointment_id?`, `status` (`draft`, `completed`, `abandoned`), `kind` (`sale`, `credit_note`), `original_sale_id?` (avoir), `number` (série continue), totaux HT / TVA / TTC / remises, `currency`, `idempotency_key` (unique), `completed_at/by`, **`prev_hash`, `hash`** |
| `sale_lines` | `kind` (`service`, `product`, `deposit_applied`, `custom`), référence, **libellé et prix figés**, quantité, `unit_price`, remise (montant ou %), `discount_reason`, `discount_approved_by?`, taux de TVA **figé**, totaux de ligne, `staff_id` (pour les statistiques et commissions futures) |
| `sale_payments` | `payment_method_id`, `amount`, `change_given` (espèces), `external_ref?` (n° de transaction TPE, **jamais de numéro de carte**), `received_at` |
| `deposits` | Acompte : client, rendez-vous, montant, ticket d'encaissement, statut (`open`, `applied`, `refunded`), ticket d'utilisation |
| `invoices` | Document fiscal émis à partir d'un ticket : `series` (`F`, `A` pour avoir…), `number`, `year`, **instantané** des mentions vendeur + acheteur (B2B : raison sociale, adresse, n° TVA), `pdf_path`, `pdf_sha256`, `prev_hash`, `hash` |
| `closures` | Clôtures **journalières (Z), mensuelles, annuelles** : totaux par taux / moyen de paiement, **grand total perpétuel**, nombre de documents, chaînage |
| `fiscal_journal` | Journal des événements (ouverture/clôture, validation, avoir, abandon de brouillon, réimpression, export, changement de paramètres fiscaux) — **ajout seul, chaîné** |
| `export_batches` | Exports comptables générés (période, format, empreinte, auteur) |

### 4.4 Règles de calcul (côté serveur)
- Prix catalogue **TTC** (usage salons B2C), TVA extraite par taux ; option HT pour le B2B (décision D8).
- Remise de ligne puis remise de ticket répartie au prorata, arrondi par profil pays ; somme des lignes = total du ticket (test d'invariant).
- Paiement mixte : Σ paiements = total TTC ; l'excédent espèces devient `change_given` ; aucun excédent non-espèces accepté.
- Acompte : encaissé comme ticket (facture d'acompte si le pays l'exige, ex. France) puis **imputé** sur le ticket final (ligne `deposit_applied` négative).
- Avoir / remboursement : nouveau document `credit_note` lié au ticket d'origine, montants négatifs, moyen de remboursement, **plafonné** au montant restant remboursable (concurrence testée).

## 6. Parcours iPhone (identité SOLUSSIMO conservée)

1. **Caisse** (onglet existant) : état de la session (ouverte / fermée), CA du jour, bouton principal **« Encaisser »**.
2. **Ouverture** : fond de caisse saisi par coupures (pavé numérique, gros boutons).
3. **Encaisser** :
   - depuis un rendez-vous du planning ou de la fiche client : **ticket prérempli** (prestation, prix, collaborateur, client) ;
   - ajout de produits / prestations par recherche ; remise par ligne ou globale (feuille dédiée, motif) ;
   - **paiement** : grand total, boutons de moyens de paiement, **paiement mixte** par montants partiels, calcul du rendu monnaie ;
   - confirmation → **reçu** : partager (feuille iOS), envoyer par e-mail, afficher le QR / PDF ; facture nominative si demandée.
4. **Historique** : tickets du jour, détail, **avoir / remboursement** en 2 gestes avec motif.
5. **Clôture** : comptage par coupures, écart affiché, justification si écart, **ticket Z** (PDF).
6. **Rapports** : CA par jour / semaine / mois, par collaborateur, prestation, moyen de paiement ; exports (owner/admin).

Exigences : zones tactiles ≥ 44 px, montants en grand, aucune saisie au clavier texte pour les montants (pavé numérique), confirmation claire de chaque paiement, retour haptique visuel, **aucune double validation possible** (bouton désactivé + idempotence serveur).

**4 langues** : nouveaux espaces `register.*`, `sale.*`, `payment.*`, `invoice.*`, `reports.*` ; formats monétaires via `Intl.NumberFormat` ; **les PDF sont émis dans la langue du profil pays** (mentions légales) avec traduction facultative pour le client.

## 7. Génération des PDF

| Option | Avantages | Inconvénients |
| --- | --- | --- |
| A. **Côté serveur** (Supabase Edge Function, bibliothèque PDF) | Document unique et figé, empreinte SHA-256 calculée côté serveur, stockage Supabase Storage (privé) | Déploiement d'une fonction serveur (autorisation requise) |
| B. Côté iPhone (pdf-lib dans le navigateur) | Pas de serveur supplémentaire | Le PDF n'est pas une source de vérité ; empreinte non garantie |

**Recommandation : A** — le PDF est généré une fois, stocké (bucket privé, RLS), son empreinte est enregistrée dans `invoices`, et toute réimpression est journalisée et marquée « duplicata ».

## 14. Critères d'acceptation (démonstration sur iPhone, données fictives)

1. Ouvrir la caisse avec un fond de 150 € compté par coupures.
2. Depuis un rendez-vous terminé : ticket prérempli, ajout d'un produit, remise de 10 % avec motif, paiement **20 € espèces + reste carte**, rendu monnaie correct, reçu partagé via iOS.
3. Encaisser un **acompte** à la réservation puis l'imputer sur le ticket final.
4. Émettre un **avoir partiel** (remboursement espèces) avec motif ; le ticket d'origine reste intact.
5. Tenter une remise de 40 % en tant que collaborateur → validation d'un responsable demandée.
6. Clôturer : écart de caisse affiché et justifié, ticket Z PDF, rapport du jour cohérent avec le Z.
7. Exporter le journal des ventes (CSV, FEC) du mois.
8. Un autre salon ne voit aucune vente ; un collaborateur ne voit que ses établissements.
9. Interface complète en FR, EN, ES, DE ; bandeau « mode non certifié — données fictives » visible.
